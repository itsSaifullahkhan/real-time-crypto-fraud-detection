# Historical Market Data Design

## 1. Purpose

This Phase 4 document defines the historical Coinbase market dataset that will later enrich Python-generated historical customer transactions. It specifies the source, products, fixed date range, granularity, raw candle fields, storage layout, request-window strategy, missing-data policy, and future point-in-time enrichment design.

This phase is design only. It does not download Coinbase data, call APIs, create Parquet files, create ADLS or Unity Catalog resources, implement Databricks tables, or calculate features.

## 2. Role of Historical Market Data

Historical market data provides real public BTC-USD and ETH-USD market context for simulated customer transactions. It will later support:

- Latest market price at transaction time.
- Five-minute price change.
- Five-minute rolling volatility.
- Five-minute trading volume.
- Customer transaction USD valuation.
- Market-context candidate features.

## 3. Real Versus Simulated Data Boundary

Coinbase historical candles are real public market data only. They are not customer transaction data, fraud data, account data, withdrawal data, or confirmed fraud labels.

Customer accounts, devices, wallets, authentication events, customer transactions, fraud scenarios, and delayed labels remain simulated data generated by later Python components.

## 4. Official Source Design

The approved source is the official Coinbase Exchange historical candle endpoint concept:

```text
GET /products/{product_id}/candles
```

The full downloader will be implemented in a later phase. Phase 4 stores only non-secret design settings in `config/historical-market-data.yaml`.

## 5. Products

Only these products are in scope:

- `BTC-USD`
- `ETH-USD`

No additional products should be downloaded or configured without a future approved contract change.

## 6. Historical Time Range

The fixed reproducible period is:

```text
Start: 2026-01-01T00:00:00Z
End:   2026-06-30T23:59:59Z
```

Historical Python customer activity created later must use the same overall time period.

## 7. One-Minute Granularity Decision

Granularity is fixed at 60 seconds, representing one-minute candles.

One-minute candles are detailed enough for portfolio-grade five-minute market windows while keeping the historical data volume manageable. They also align with later feature needs without forcing trade-level historical reconstruction.

## 8. Raw Candle Fields

Raw candle records use `config/schemas/historical-market-candle.schema.json`.

| Field | JSON type | Target Delta type | Required | Description |
| --- | --- | --- | --- | --- |
| `schema_version` | string | STRING | Yes | Initial value `1.0`. |
| `source` | string | STRING | Yes | Must equal `coinbase_exchange_rest_api`. |
| `product_id` | string | STRING | Yes | `BTC-USD` or `ETH-USD`. |
| `candle_start_timestamp` | string | TIMESTAMP | Yes | Start of one-minute UTC interval. |
| `candle_end_timestamp` | string | TIMESTAMP | Yes | End of one-minute UTC interval. |
| `granularity_seconds` | integer | BIGINT | Yes | Must equal `60`. |
| `open_price_usd` | number | DECIMAL(20, 8) | Yes | Opening price. |
| `high_price_usd` | number | DECIMAL(20, 8) | Yes | Highest price. |
| `low_price_usd` | number | DECIMAL(20, 8) | Yes | Lowest price. |
| `close_price_usd` | number | DECIMAL(20, 8) | Yes | Closing price. |
| `volume` | number | DECIMAL(20, 8) | Yes | Coinbase base-asset trading volume. |
| `retrieved_at` | string | TIMESTAMP | Yes | Time our collector received the record. |

JSON Schema uses JSON `number`. Databricks tables should later use fixed-precision types such as `DECIMAL(20, 8)` for prices and volume where appropriate.

Natural business key:

```text
product_id + candle_start_timestamp
```

## 9. Difference Between Historical Candles and Live Trades

`market-event.schema.json` remains the contract for future live WebSocket trade-level market events. It includes trade ID, trade price, trade size, buy/sell side, trade timestamp, message timestamp, and sequence number.

Historical Coinbase candles do not provide those trade-level fields. The project must not fabricate trade IDs, buy/sell side, message sequence numbers, or fake individual trades. Raw historical candles therefore use the separate `historical-market-candle.schema.json` contract.

## 10. API Request-Window Design

Coinbase can return at most 300 candles per request. With 60-second granularity, one request covers up to 300 minutes, or five hours, for one product.

The later downloader must divide the fixed date range into deterministic request windows per product. It must not repeatedly request the same completed interval once that interval has been checkpointed successfully.

## 11. Pagination and Checkpoint Design

The later downloader should checkpoint progress by:

- Product ID.
- Request window start.
- Request window end.
- Granularity.
- Retrieval status.
- Retrieval timestamp.

Checkpointing lets the downloader resume without redownloading completed windows. Duplicate candles must still be removed by `product_id + candle_start_timestamp`.

## 12. Retry and Backoff Design

Retries must use backoff. The downloader should distinguish transient request failures from permanent validation failures.

Phase 4 does not define exact retry counts or production timeout settings. Those are implementation parameters for the later downloader.

## 13. Missing-Interval Policy

Historical intervals may be absent when Coinbase has no ticks.

Rules:

- Do not silently create fake Coinbase candles.
- Preserve information that an interval was missing.
- Do not use a future candle to enrich an earlier customer transaction.
- A previous completed candle may later be carried forward only within a documented maximum freshness tolerance.
- Records outside the freshness tolerance should be flagged.
- Final tolerance will be calibrated during implementation.
- Missing-data indicators must be available as data-quality metadata and must not secretly change the fraud label.

## 14. Deduplication Key

Duplicate raw candles are removed using:

```text
product_id + candle_start_timestamp
```

If duplicate rows disagree on OHLCV values, the future ingestion process should quarantine or flag the conflict rather than silently choosing one without audit metadata.

## 15. Timestamp Rules

All timestamps are UTC ISO 8601 strings with timezone information.

Rules:

- `candle_start_timestamp` is the beginning of the one-minute interval.
- `candle_end_timestamp` must equal `candle_start_timestamp + 60 seconds`.
- `retrieved_at` is when our collector received the record.
- Future enrichment must compare customer transaction event time to candle interval time using event-time semantics.

## 16. ADLS Folder Layout

Conceptual raw storage path:

```text
ADLS container
`-- raw/
    `-- historical/
        `-- market_candles/
            |-- product_id=BTC-USD/
            |   `-- event_date=YYYY-MM-DD/
            `-- product_id=ETH-USD/
                `-- event_date=YYYY-MM-DD/
```

Physical Parquet files will be stored later. This phase does not create an ADLS account, container, external location, storage credential, volume, catalog, schema, or Delta table.

## 17. Unity Catalog Governance Role

Unity Catalog will later provide governed access to the raw and processed market datasets through an External Volume or another approved governed storage arrangement.

Phase 4 documents the intended structure only. No Unity Catalog objects are created.

## 18. Raw-to-Bronze Future Flow

Future flow:

```text
Raw historical Coinbase candles
-> bronze.historical_market_candles
-> silver.market_bars_1m
```

Raw datasets remain separate:

```text
raw/historical/market_candles/
raw/historical/accounts/
raw/historical/devices/
raw/historical/wallets/
raw/historical/authentication_events/
raw/historical/customer_transactions/
raw/historical/fraud_labels/
```

Coinbase market candles are real market data. The other historical datasets are simulated customer and fraud-related data.

## 19. Silver Normalized Market-Bar Design

The future `silver.market_bars_1m` table should normalize candle records into a clean one-minute market state. Candidate normalized fields include product ID, candle timestamps, open, high, low, close, volume, retrieval metadata, missing-interval flags, duplicate flags, and quality status.

No Silver table is created in Phase 4.

## 20. Future Customer-Transaction Enrichment

Future flow:

```text
Generated customer transactions
-> bronze.customer_transactions
-> silver.customer_transactions
```

Then:

```text
silver.customer_transactions
+
silver.market_bars_1m
-> point-in-time market enrichment
-> offline transaction features
-> delayed-label join
-> model training
```

## 21. Point-in-Time Correctness

Future enrichment must:

- Match transaction asset with product ID.
- Map `BTC` to `BTC-USD`.
- Map `ETH` to `ETH-USD`.
- Use the most recent completed candle available at or before the transaction timestamp.
- Never use a future candle.
- Record the matched candle timestamp.
- Record market-data freshness.
- Flag transactions where no valid prior market candle exists.

The Spark join is not implemented in Phase 4.

## 22. Offline/Online Consistency

Raw historical and live market inputs differ:

```text
Historical:
Coinbase one-minute candles

Live:
Coinbase WebSocket trade-level events
```

Both paths must later produce the same normalized market-state definitions:

- Latest market price.
- Price change over five minutes.
- Volatility over five minutes.
- Volume over five minutes.
- Market-data freshness.

Historical features will be calculated from past candles. Live features will be calculated from trade events and streaming state.

The same product mapping, event-time rules, five-minute window definition, timezone, null handling, freshness policy, and aggregation formulas must be used.

All market features remain: `Design candidate - definition to be finalized in Phase 8.`

## 23. Data-Quality Checks

Future data-quality checks should validate:

- JSON Schema conformity before raw persistence where applicable.
- Product ID is `BTC-USD` or `ETH-USD`.
- Granularity is 60 seconds.
- Prices are greater than zero.
- Volume is zero or greater.
- `high_price_usd` is not lower than open, close, or low.
- `low_price_usd` is not higher than open, close, or high.
- `candle_end_timestamp = candle_start_timestamp + 60 seconds`.
- Duplicate natural keys.
- Missing intervals.
- Stale market data during transaction enrichment.

## 24. Cost and Volume Considerations

The fixed six-month, two-product, one-minute design is small enough for a student portfolio project while remaining realistic.

Approximate expected maximum intervals:

```text
181 days * 24 hours * 60 minutes * 2 products = 521,280 product-minute intervals
```

Actual candle count may be lower because Coinbase can omit intervals without ticks.
